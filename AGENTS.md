## What this project is

ALSHost is a minimal UE 5.8 host project built to run and extend the ALS-Community-UE5 locomotion plugin (vendored directly under `Plugins/ALS-Community-UE5`, not a submodule — we don't push changes upstream). Live editor control comes from Epic's own `ModelContextProtocol` + EditorToolset, and a second, more capable plugin, `ClaudeUnrealMCP` (git submodule → `AgustinJimenez/ClaudeUnrealMCP`). Durable facts about this codebase live under `docs/`: `asset-audit.md`, `mcp-notes.md`, `architecture.md`, `testing.md` — read those before re-deriving the same facts. Per-task blow-by-blow logs live under `AGENT_TASKS/` for anything non-trivial.

**Core philosophy**: when ClaudeUnrealMCP can't do something we need, extend it (it's our own submodule/repo) rather than working around the gap forever. A one-off Python/console workaround is fine to get unblocked in the moment, but if the same class of problem will recur, build the tool, commit, push, bump the submodule pointer. This has happened repeatedly: `add_socket`/`set_socket_transform`/`list_sockets`, `retarget_anim_asset` (wraps `EditorAnimUtils::RetargetAnimations`, no Blueprint/Python exposure otherwise), `import_texture` (legacy synchronous `UTextureFactory` path, sidesteps a TaskGraph recursion crash), `set_anim_notify_property` (AnimNotify properties are Python-protected), and a fixed `set_pin_default` (see below).

## Engine/tooling gotchas (apply broadly)

- **Python console reflection is more restricted than it looks.** Many normal UPROPERTYs (AnimGraph Nodes arrays, graph-node `NodeGuid`, `Skeleton::Sockets`, `Material.expressions`) throw "protected and cannot be read/set" from Python's generic `get_editor_property`/`set_editor_property`, with no consistent rule for which. Fallbacks: `execute_console_command`'s `obj dump "<full object path>"` almost always works for *reading* (quote any path segment with a space); for *writing*, either use the object's real BlueprintCallable accessor function (e.g. `component.set_skeletal_mesh(mesh)`, not the raw property) or build a proper ClaudeUnrealMCP C++ handler using the correct native API.
- **AnimGraph state machines aren't in `FunctionGraphs`/`UbergraphPages`.** Each state/transition has its own nested graph; only a recursive `GetSubGraphs()` walk from the top-level graphs finds them. `read_function_graphs` does not descend into these.
- **Never remove a Blueprint graph node via raw `RemoveNode()`.** It doesn't break pin links or notify Blueprint extensions — for an AnimGraph state-machine sub-graph node this leaves `AnimBlueprintExtension_StateMachine`'s cached `TargetRootNode` dangling and crashes the editor on a *later* compile. Always use `FBlueprintEditorUtils::RemoveNode()`.
- **`execute_console_command` never returns its output** (including `py` scripts) — always follow with `read_log` or read the `Saved/Logs` file directly. A crashed editor process just looks like a generic MCP connection error; check `Get-Process -Name UnrealEditor` before assuming a network hiccup. If `read_log` itself errors on a bad relative path, grep `Saved/Logs/ALSHost.log` directly (check `ls -la` timestamps first — a prior session/relaunch can leave several `ALSHost*.log`/backups, only the most recently modified one is the live editor's).
- **Adding a UPROPERTY field to a struct used by a DataTable cannot go through Live Coding.** `LiveCoding.Compile` patches the running process only, doesn't touch the base `.dll`, and re-points existing DataTable assets at a transient reinstanced struct (`RowStruct=.../Transient.LIVECODING_<Name>_0`) — saving the DataTable in that state silently drops the new fields (no error, they just don't appear in the row text). Editor restart alone doesn't fix it either, since restart just reloads the old unpatched `.dll`. The only clean path: close the editor fully, run a real build (`Build.bat <Target>Editor Win64 Development -project=...`), then relaunch — verify first via `obj dump` on the DataTable that `RowStruct` resolves to `/Script/...` (not `Transient.LIVECODING_...`).
- **`reload_mcp_server` hard-restarts the Node bridge**, killing the calling session's own connection — recover via the `/mcp` slash command, not a full restart.
- **Plugin content is mounted under the `.uplugin` filename, not the folder/FriendlyName** (ALS-Community-UE5's is `ALSV4_CPP.uplugin` → `/ALSV4_CPP/...`). `search_assets`/`list_blueprints` only search `/Game` and miss plugin content entirely — find a plugin asset's real path by grepping the raw `.uasset` bytes on disk for a known string (`strings -n 8 X.uasset | grep ...`).
- **`set_component_property` (and similar raw-property tools) don't force a Blueprint recompile** — they mark the Blueprint dirty but PIE still runs the last *compiled* generated class. Always follow with `compile_blueprint` before testing in PIE if the change needs to show up there.
- **`set_physics`/`set_collision` (ClaudeUnrealMCP) infer the target component from the actor's `RootComponent`, not by name.** If an actor's serialized `RootComponent` is stale (e.g. after a C++ change that reparents the root — see pickup-physics below), the call silently lands on the *wrong* component with no error. Always read back every primitive component on the actor, not just the one intended, before concluding a "no visible effect" call was a no-op.
- **Codex has its own MCP config** (`~/.codex/config.toml` or a trusted project's `.codex/config.toml`), separate from `~/.claude.json`. Check `codex mcp list`/`codex mcp get <name>`. Its stdio command must launch this project's `MCPServer/index.js` with `UE_HOST=127.0.0.1 UE_PORT=9877`; Epic's server registers separately as Streamable HTTP at `http://127.0.0.1:8000/mcp` (needs `ModelContextProtocol.StartServer 8000` run first, doesn't persist across restarts). Restart Codex after any config change — it snapshots tools at session start.
- **Claude Code's own MCP registration is keyed by an exact project directory string in `~/.claude.json`**, and that key does not necessarily match a Bash tool's cwd — it must match the *session's own* reported project scope (visible in the `/mcp` UI). Which directory is "the real scope" varies session to session; when a server that used to work stops appearing, check `~/.claude.json` for duplicate/conflicting scope-key entries against the current session's actual scope, re-run `claude mcp add` from a shell whose cwd matches it, and restart the CLI (`/mcp` alone only reconnects already-known servers, it doesn't discover newly-added ones).
- **Two "official" and "community" socket tools operate on different layers.** `SkeletalMeshTools.add_socket` (Epic official) is mesh-level; ClaudeUnrealMCP's `add_socket` is skeleton-level (shared across every mesh bound to it). A mesh-level socket overrides a same-named skeleton-level one — know which layer an existing socket lives on before editing it with the other tool.
- **For a retarget-chain rotation bug more than 1-2 bones deep, stop reasoning from raw XYZ numbers and build a real visualization — but verify any candidate fix against *multiple* points across the whole timeline, not one frame.** Sampled bone positions via `compare_anim_bone_pose` into an interactive 3D pose viewer (Three.js Artifact — skeleton + translucent capsule body mesh toggle + a facing-direction arrow since "screen-left" isn't "character's left" once you've orbited a free 3D view + floating labels pinned to specific bones via `Vector3.project(camera)`), then opened it in a real browser via the `chrome-devtools` MCP (`file://` the local HTML — the hosted artifact URL needs auth that browser doesn't have) and actually looked at screenshots — this turns "guess an axis, wait ~30s per retarget cycle, check numbers, repeat" into "look at the picture." **But a single sampled frame (even a deliberately-picked one) can coincidentally look right while the rest of the clip is still badly wrong** — `AS_Punch_Cross`'s left-arm chain fix looked correct checked only at t=0.3s, then turned out to swing wildly behind the torso at every other frame once actually checked; always sample several timeline points (rest, mid, end) before trusting a chain-rotation fix, the same discipline as the earlier "diff against a known-good reference, not just two frames of the same clip" lesson but one level further.
- **`capture_screenshot` is fixed (2026-09-02) and now genuinely works — it produces a real, readable PNG.** The old implementation just called `FScreenshotRequest::RequestScreenshot()` and returned immediately; that only *queues* a capture that's written asynchronously on a later frame/thread with no completion signal, so the file frequently didn't exist yet when the handler returned (this cost real debugging time across multiple sessions before being root-caused, not just assumed broken). Rewritten in `MCPServerBlueprintRuntimeFixes.cpp::HandleCaptureScreenshot` to read the active level viewport's pixels back synchronously (`FLevelEditorModule::GetFirstActiveLevelViewport()` → `FViewport::ReadPixels`, which internally flushes rendering commands) and encode/write the PNG on the same thread before responding — needed the `RenderCore` module added to `ClaudeUnrealMCP.Build.cs` for `FlushRenderingCommands`. Still verify with real accessor functions (`get_skinned_asset()`, `get_bounds()`, etc.) for anything that doesn't need an actual eyeball check, but a real screenshot is now genuinely usable for visual debugging.
- **New MCP tool: `save_all_and_close`** — saves all dirty packages then cleanly exits the editor (`FGenericPlatformMisc::RequestExit`, deferred one tick via `GEditor->GetTimerManager()->SetTimerForNextTick(...)` so the response reaches the client before the process dies). Useful to end a session cleanly instead of leaving the editor running or killing the process externally. The connection drops when the editor exits, same as any other editor-closed scenario — relaunch normally to reconnect.
- **The "save immediately, before anything that could force-kill the editor" rule applies to every content-mutating call**, not just obvious ones: `set_component_property`, `set_blueprint_cdo_property`, `add_input_mapping`, level actor placement, and asset-*creation* calls (`import_file`, `import_texture`, `create_*`) all need their own `save_asset` before a rebuild/relaunch, or the change is silently discarded. A change that reads back correctly via `read_class_defaults`/`get_editor_property` immediately after setting it is *not* proof it survived — after any relaunch, re-verify (not just trust a prior save) anything that matters.
- **A tool can report success, and even produce a correctly-formatted file, while writing to the wrong file entirely.** Root-caused once: ClaudeUnrealMCP's `save_asset`/`save_all` always wrote level packages with the `.uasset` extension instead of `.umap` (fixed by checking `Package->ContainsMap()` and using `FPackageName::GetMapPackageExtension()`). If a "saved and verified" change keeps reverting across sessions despite every check passing, consider that the tool might be writing a different file than the one being checked — read the tool's own source rather than trying a third workaround.
- **PIE-blindness**: every actor-query tool (`list_actors`, `find_actors_by_name`, `get_scene_summary`, raw `GameplayStatics.get_all_actors_of_class`) resolves to the *editor* world, never the running PIE world — level-placed actors are visible in both (duplicated at PIE start) but anything spawned dynamically at runtime, including the player pawn, is invisible to every MCP tool. The real fix is CQTest (see below), not reaching into PIE externally.
- **Compiling a Blueprint while an instance of it is live-ticking in PIE can hard-crash the engine** (`Pure virtual not implemented`), not just read stale data — call `play_in_editor` with `operation: "status"` before any `compile_blueprint`, and `operation: "stop"` first if `is_playing` is true. Don't ask the user to check or guess from context.
- **`ALS.Weapon.ShowDebugTrace`, `ALS.Interact.ShowDebugTrace`, and the `ALS.HeldObject.Tune*` cvars are console-only and don't persist across an editor relaunch** (but the Tune* ones *do* persist across a mere Play/Stop cycle within the same process — zero them explicitly for a clean baseline). `Interchange.FeatureFlags.Import.FBX 0` also doesn't persist — re-set at the start of every fresh editor session before any scripted FBX import.
- **Enhanced Input mapping-context edits don't apply to an already-running PIE session** — stop and re-press Play, don't assume a correctly-saved binding change is broken.

## Held-object / weapon system

`AALSCharacter` has one `HeldObjectRoot` scene component with a StaticMeshComponent and a SkeletalMeshComponent attached under it — one rigid prop and one animated prop max at a time. `AttachToHand` (BlueprintCallable C++) snaps `HeldObjectRoot` onto a virtual bone (`VB RHS_ik_hand_gun`/`VB LHS_ik_hand_gun`) with optional location/rotation offsets. Per-weapon logic lives in Blueprint: `ALS_CharacterBP::OnUpdateHeldObject` switches on `EALSOverlayState` and calls `AttachToHand` with a hardcoded mesh per case. To add a weapon: repoint an existing case's mesh pin, extend the enum, or call `AttachToHand` directly. Weapon meshes are SkeletalMeshes (not StaticMesh) so parts can animate — sockets (Muzzle, ADS) live on the weapon's own Skeleton asset, added/verified via `add_socket`/`set_socket_transform` and (once available) `SceneTools.trace_world`/`get_bounds` rather than eyeballed from bounding boxes.

`UALSWeaponFireComponent` (ALSHost's own Source module, added to `ALS_CharacterBP`) binds its own Enhanced Input actions directly via `BindAction` in both `BeginPlay` and `ReceiveControllerChangedDelegate` (a pawn's `BeginPlay` commonly precedes controller possession — every self-binding input component in this project follows this pattern). Fire() traces from the muzzle socket toward a point projected along the camera's forward vector (visual origin, aimed convergence). Spread/bloom scale with gait and aiming; full-auto fires once on press then repeats at a RPM-derived interval. Ammo is a `TMap<EALSOverlayState, FALSWeaponAmmoStats>`; `Reload()` pulls from `UALSInventoryComponent`'s matching `AmmoItemID` reserve at reload-start (refunded if cancelled by a weapon swap) and no-ops on zero reserve.

## Testing (CQTest)

CQTest + CQTestEnhancedInput (real engine plugins, in `ALSHost.Build.cs`) run as engine code compiled into ALSHost, so `GWorld` correctly follows into PIE — this is the only way to reach live gameplay state, and closes the PIE-blindness gap. Run headlessly: `UnrealEditor-Cmd.exe -ExecCmds="Automation RunTests ALSHost;Quit" -unattended -nopause -nullrhi`; read results from `Saved/Logs/ALSHost.log`. Existing coverage: `Source/ALSHost/Private/Tests/*.cpp` — extend these rather than starting fresh.

Gotchas:
- `FActorTestSpawner` does **not** call `BeginPlay` — use `FMapTestSpawner::CreateFromTempLevel` for anything needing real actor lifecycle.
- `FMapTestSpawner`'s temp level has **no floor** — a spawned character free-falls indefinitely; call `DisableMovement()` for anything that needs to stay still, and call it **after** `Possess()`, never before (possession silently resets movement mode).
- `UGameplayStatics::GetPlayerPawn` only resolves through the world's actual first local player, not just any spawned `APlayerController`.
- A `SpawnActorAt<T>(...)` call into an already-playing world runs `BeginPlay()` synchronously inside the call — a property `BeginPlay()` reads once and locks in (e.g. into a `SetTimer`) can't be tuned by setting it on the returned reference afterward.
- **Never capture a `TEST_METHOD`-local pointer by reference into a `TestCommandBuilder` lambda that isn't guaranteed to run before the method returns** (i.e. across a `.Then()`/`WaitDelay()` boundary) — promote it to a `TEST_CLASS` member field first, or it's a dangling-reference crash on the deferred command.
- `UUserWidget::NativeConstruct` does not appear to fire at all for a widget created via `CreateWidget`+`AddToViewport` under headless `-nullrhi` — BindWidget/delegate-subscription logic done there is currently unverifiable by CQTest. Verify UMG-level changes live (`read_widget_tree`/`compile_blueprint`) instead. (Montage/animation *playback state*, e.g. `GetCurrentActiveMontage()`, IS observable under `-nullrhi` — don't assume all visual state is untestable.)
- When a Blueprint gains a new baked-in component that a test used to fake with a dynamically-added one, check whether the test now creates a **duplicate** independent component (both bind the same delegate, only one gets the test's overridden values) — a stale "X doesn't have Y" comment is a common tell.
- A probability check against `FMath::FRand()` (uniform `[0,1)`) needs `>=`, not `>`, to correctly treat an exact `0.0` chance as "never" — work boundary cases out on paper.

## Content pipeline: migrating/retargeting animations & assets

**Universal Animation Library → ALS**: follow [docs/animation-import.md](docs/animation-import.md). Use the Unreal/Godot GLB, consistent centimeter units, and the clean IK retargeter; verify the whole motion and actual mesh before replacing assets. The old Unity-FBX scale/rotation workarounds are historical, not the current recipe.

**From another UE project with ClaudeUnrealMCP**: `AssetToolsHelpers.get_asset_tools().migrate_packages(...)` (Python-exposed `IAssetTools::MigratePackages`) must run from the *source* project's own editor session (MCP is just a TCP client to whichever editor is running). Build the package array as `unreal.Array(unreal.Name)` of path strings — passing `unreal.Array(unreal.Package)` of loaded objects doesn't raise an error, it silently nativizes each object's string repr and writes to a garbage destination path (only visible by reading the `AssetTools:` log line, not the tool's return value).

**From a project without ClaudeUnrealMCP** (e.g. only Epic's official server): compute the package dependency closure via BFS over `AssetTools.get_dependencies`, then raw-copy the resulting `.uasset` files by relative path on the filesystem — the destination editor auto-discovers new files live, no restart needed.

**Retargeting onto a different skeleton**: an `AnimSequence` is bound to one specific `Skeleton`; duplicating the file doesn't change that. If the bone hierarchy/naming genuinely matches (check live via `get_bone_children`, don't assume from "looks similar"), `retarget_anim_asset` does a clean bone-name remap. **Always verify a freshly retargeted animation before trusting it**: sample 2-3 distinct, non-adjacent bones (e.g. `pelvis`, `hand_r`, `foot_r`) via `compare_anim_bone_pose` (works even sampling an animation against itself) and confirm the returned world positions are actually distinct — a broken retarget can silently collapse every non-root bone to the same point (only the root/pelvis track transfers), which visually manifests as the character's skeletal mesh vanishing entirely (an invalid-pose safety response) the instant that animation plays. This is invisible to CQTest's own montage coverage, since `GetCurrentActiveMontage() != nullptr` says nothing about pose validity. If a retarget is suspect, check whether the source FBX export had an unwanted "bake only root" toggle rather than assuming the retarget tool itself is at fault.

## FBX/texture import crashes (TaskGraph recursion)

`AssetTools.import_asset_tasks` (the standard scripted FBX/texture import) can crash the editor outright with `Assertion failed: ++Queue(QueueIndex).RecursionGuard == 1 [TaskGraph.cpp:705]` — calling Interchange's own nested TaskGraph work synchronously from inside ClaudeUnrealMCP's own queued command handler. Confirmed triggers: any `Texture2D` import via this path, and (separately, sometimes even with `embed_textures=False`/mesh-only) a fresh Blender-exported FBX in general. Two working fixes, not mutually exclusive:
1. **Textures**: use `import_texture` (ClaudeUnrealMCP) — calls `UTextureFactory::FactoryCreateBinary` directly, the pre-Interchange synchronous path, never touches the TaskGraph.
2. **FBX**: run `Interchange.FeatureFlags.Import.FBX 0` first (forces the legacy synchronous FBX factory) — doesn't persist across relaunch, re-set every session.

A full Sketchfab-model-via-Blender pipeline that works end to end: download in Blender → re-save any image whose `filepath` went stale (Sketchfab's temp dir gets deleted post-import; set `image.filepath_raw` to a new path and `image.save()`, re-encodes from the already-loaded pixel buffer) → export mesh-only FBX (`embed_textures=False`) → import with `Interchange.FeatureFlags.Import.FBX 0` set and `import_materials=False, import_textures=False` → `import_texture` per PBR map (normal maps need `CompressionSettings=TC_Normalmap`; packed data textures need `TC_Masks`+`SRGB=False`) → build the material graph via `MaterialEditingLibrary.create_material_expression(...)` return values directly (never call `mat.get_editor_property("expressions")` — protected, see above) → `mesh.set_material(0, mat)` (the instance method, not `EditorStaticMeshLibrary.set_material` which doesn't exist in this engine version).

**A `replace_existing=True` in-place reimport can silently no-op** — report the correct new source path in the log, yet leave the asset's actual bounds/geometry bit-for-bit identical to before. If a reimport doesn't visibly change anything, don't retry it — import fresh under a new name (e.g. `_v2` suffix) and verify (bounds, dependency count, etc.) before trusting it, and before deleting the old one check nothing still references it (`delete_asset` will refuse).

**A multi-package FBX import's auxiliary packages (Skeleton/PhysicsAsset/AnimSequence siblings) aren't reliably flushed by `task.save = True` alone**, and `search_assets`/the in-memory asset registry showing them present is not proof they're on disk (only a direct filesystem check is). After any multi-asset import, explicitly call `unreal.EditorLoadingAndSavingUtils.save_dirty_packages(save_content_packages=True)` and verify on disk before anything that might crash/force-kill.

**After any editor crash+relaunch, don't trust `execute_console_command`'s `"executed": true` (or even a correctly-echoed `Cmd: py` log line) as proof a Python script actually ran** — it's been observed silently no-op'ing entirely (no `print()` output, no file write, no spawned actor) across consecutive relaunches while non-Python console commands kept working fine on the same connection. Sanity-check with a trivial, independently-observable side effect (a file write checked from outside Unreal) before trusting a batch of `py` calls whose success matters.

## Blender ↔ Unreal round-trip notes

- Blender's local mesh coordinates match Unreal's local coordinates directly except **Y is negated** between the two engines.
- `bpy.ops.object.origin_set(type='ORIGIN_CURSOR')` shifts vertices and compensates via `obj.location` — but **the FBX exporter bakes `obj.location`/`rotation`/`scale` into the exported vertices**, so that compensation gets re-added at export time and nets out to nothing. Fix: zero `obj.location`/`obj.rotation_euler` immediately before export (after `origin_set`, which needs the original location to compute the shift correctly).
- Only zero the specific transform components a fix actually needs — a Blender import commonly carries a real unit-conversion scale (e.g. `0.01`) that has nothing to do with a pivot fix and will silently balloon/shrink the mesh 100x if blindly reset to `(1,1,1)`.
- Exporting an already-imported Unreal asset back out via ClaudeUnrealMCP's `run_python` `export_fbx` op is a reliable way to recover a source file when the original download/`.blend` is gone.

## UMG/widget authoring gotchas

- **A `UUserWidget` meant to be embedded in a Vertical/HorizontalBox needs a `SizeBox`, `ScrollBox`, or similar content-driven-size panel in its tree** — a bare `CanvasPanel` root reports no meaningful desired size when auto-sized by a parent, so it renders (and hit-tests) at effectively zero size.
- **`add_widget`'s CanvasPanel-child `width`/`height` params default to 200x50** — any widget added as a direct `CanvasPanel` child without explicit sizing silently gets clipped to that box (both rendering and hit-testing) once real content is added. Set real size at add-time, or via the `LayoutData` struct property afterward (`Offsets`/`Anchors`/`Alignment` are sub-fields of `FAnchorData LayoutData`, not independently top-level-reflected — setting them directly fails with "property not found").
- **A widget embedded via `AddChildToCanvas` inside another widget has two independent size constraints**: its own root `CanvasPanel`'s sizing of its own content, and the *embedding* slot in the parent that determines how much of that content is actually let through. Resizing one without the other is a classic "I fixed it but nothing changed" symptom that won't show up reading the child's own `LayoutData`.
- **`USizeBox`'s `WidthOverride`/`HeightOverride`/`MinDesiredWidth`/etc. are no-ops unless the matching `bOverride_<Name>` boolean is also set true** — the Designer UI pairs each with a checkbox; this MCP workflow has no equivalent affordance, so setting only the numeric value has zero effect. Generalizes: any UMG "override" property likely has a matching `bOverride_*` boolean — `list_properties` an unfamiliar widget class before assuming one property is sufficient.
- **A cached, repeatedly shown/hidden `UUserWidget` (toggled via `RemoveFromParent`/`AddToViewport` rather than recreated) re-runs `NativeConstruct` every time it's re-added to a viewport** — including on nested child `UUserWidget`s still attached inside its tree, even when their own `UPROPERTY()` instance was never recreated. `OnValueChanged.AddDynamic`/`OnClicked.AddDynamic` aren't idempotent — a second bind trips a handled-but-noisy `ensure`. Guard any `NativeConstruct`-time delegate binding behind a `bool bDelegatesBound` member set after the first bind; keep refresh-only calls unconditional.
- **`set_widget_property`'s generic `ImportText`-based path can report success without having actually changed the right thing** (same failure family as `set_component_property`/`FClassProperty` elsewhere in this file). When a widget-property fix doesn't visibly work after a user check, use Epic's official `ObjectTools.get_properties`/`set_properties` (path form: `{"refPath": "/Game/Path/WBP.WBP:WidgetTree.WidgetName[.SlotClassName_0]"}`) to read ground truth *before* trying another fix on top of an unverified one.
- `read_widget_tree`/`set_widget_property` only find properties on the widget's own class — a child's `UPanelSlot` properties (Size, Padding, Alignment) need falling back to `Widget->Slot`'s class if not found on the widget class first (fixed in ClaudeUnrealMCP already).
- Nesting one Widget Blueprint's instance inside another's tree at design time isn't supported by any current tool — create it dynamically in `NativeConstruct` via `CreateWidget` + `AddChildToCanvas`, position via `SetAnchors`/`SetAlignment`/`SetOffsets`.

## Debugging methodology notes worth repeating

- When a symptom looks like an input-routing/timing problem but a fix at that layer changes nothing, check whether a **Blueprint event on the same shared input trigger** is doing something unconditional downstream — suspending an input mapping context only prevents an event from firing, it can't stop logic already wired to an event that still fires (found via `DebugComponent`'s Q-menu unconditionally re-selecting a stale widget state on close).
- Prefer driving facing/proximity checks off the **controller/camera rotation**, never pawn body-forward — ALS's rotation modes let the two diverge arbitrarily (e.g. frozen body-forward after strafing in Velocity Direction mode).
- A migrated-but-never-*assigned* asset (attenuation preset, material, etc.) is easy to miss when checking "is X wired up" — verify what a sound/material reference actually *is* on the object that uses it, not just that a plausible-named asset exists somewhere.
- When a "what's bound to key X" search comes up empty under `/Game`, check whether the binding actually lives in the **vendored plugin's own separate input system** (this project's `ALS-Community-UE5` ships its own `IMC_Debug`/`Debug*Action` set, independent of and easily confused with this project's own `IA_*`/`IMC_*`).
- **"Any enable X on N sub-parts, disable X on N sub-parts" pair in this engine's physics API needs the identical per-part call on both sides** — e.g. `SetSimulatePhysics(true)` alone only toggles a `USkeletalMeshComponent`'s root body; the paired `SetAllBodiesBelowSimulatePhysics(NAME_None, true/false)` call is required on *both* enable and disable, and its omission on just one side is invisible from reading the other side's code.
- Live Coding hot-reload (and even a full editor restart) does **not** retroactively update already-placed level actors' component properties from a changed C++ constructor default — `FBodyInstance`-family properties especially get serialized as an explicit per-instance blob. Existing instances need their properties set directly and resaved every time a constructor default changes; component *removal* (not property changes) does cleanly drop from already-placed actors on next load.
- A static mesh's auto-generated (FBX-import-time) simple collision can not match its own render geometry — a per-asset problem, not per-instance, affecting every actor using that mesh identically. Compare `get_bounding_box()` against the collision hull's own extents (or just regenerate via `remove_collisions`+`add_simple_collisions`) before assuming a "floating" bug is actor-level.
- Check placed-actor coordinates for exact duplicates before enabling collision on something that didn't have it before — two actors placed at identical coordinates only becomes visible as a bug once they can physically collide.

## Architecture

`ALS-Community-UE5` has ~8100 lines of real C++ (character, movement, camera, mantling, debug, math library, AI). `ALS_AnimBP` (the AngGraph) is and always will be Blueprint — Unreal's AnimGraph has no supported pure-C++ authoring path in any project. Every other plugin Blueprint is a thin config subclass, an editor-time AnimModifier, or genuinely trivial content (verified via `read_blueprint`, not assumed). See `docs/architecture.md`.

`GASP-ALS-R` (a sibling project in the same parent directory) uses Epic's newer stack instead (Mover, Motion Matching/Pose Search, GAS) — ClaudeUnrealMCP has only thin GAS scaffolding and zero support for Mover/Motion Matching. If this project moves onto that stack, expect the same pattern: hit a gap, trace the API, extend ClaudeUnrealMCP.

## Gameplay systems built so far (brief index — see AGENT_TASKS/ and git history for detail)

- **Inventory/pickups**: `UALSInventoryComponent`, `AALSPickupBase`/`AALSItemPickup`/`AALSHealthPickup`/`AALSWeaponPickup`. Pickups are press-E interact (via `IALSInteractable`), not walk-over — `Mesh` (now root, `SimulatePhysics`+`PhysicsActor` profile so items fall/settle) doubles as both the physics body and the interact line-trace target. `UALSInventoryComponent::EquipItem(FName)` is the single equip entrypoint (used by both the inventory-panel click and auto-equip-into-an-empty-hand on pickup when nothing is currently held).
- **Interaction**: `IALSInteractable` interface (`Interact`, `GetInteractionPrompt`, `SetInteractPromptVisible` — all `BlueprintNativeEvent`; **never write an explicit default `_Implementation` for one, UHT already auto-generates a no-op default**). `UALSInteractionComponent` ticks every frame finding the nearest interactable within range + a facing cone off the controller rotation, shows a world-space `UTextRenderComponent` prompt above the target. `ALS.Interact.ShowDebugTrace` cvar for diagnosing "nothing happened."
- **Doors/loot containers**: `AALSDoor` (hinge via a `SceneComponent` root + offset child mesh, rotated toward `TargetRelativeYaw` each tick — no Timeline/Curve needed), `AALSLootContainer` (grants configured `FALSLootEntry` items once, reuses ALS-Community's own `Box.Box` mesh).
- **Melee**: `UALSMeleeComponent` — always-available fist damage, bonus if carrying a knife (`ItemID="Weapon_Knife"`) or axe (`ItemID="Weapon_Axe"`, axe wins over knife rather than stacking). Also fires from left-click when `UALSWeaponFireComponent` has no equipped skeletal-mesh weapon (previously silently no-op'd for any StaticMesh-held item, i.e. always).
- **Damage zone**: `AALSDamageZone` — periodic-tick damage box trigger.
- **Footsteps**: `UALSAnimNotifyFootstep` (plugin) is baked into every mannequin locomotion/action AnimSequence's notify track, but all of them share one `HitDataTable` asset, `/Game/ALSHost/Data/DT_FootstepHitFX` (`FALSHitFX` row struct) — edit that one DataTable to change sound/decal/niagara for every character at once instead of touching ~48 individual animations. `SoundAttenuationOverride_Player`/`_NPC` fields (added on top of upstream) let `Notify()` pick `ATT_Footstep_PC` vs `ATT_Footstep_NPC` by `APawn::IsPlayerControlled()` — before this, the Sound asset's own single `AttenuationSettings` (the NPC preset) applied to everyone uniformly, which is why a cluster of enemies was audible from ~40m.
- **Death**: `UALSDeathHandlerComponent` — on `Health->OnDeath`, ragdolls the mesh (captures original collision profile/relative transform live in `BeginPlay` rather than hardcoding), disables capsule collision; `RespawnDelaySeconds > 0` schedules a full respawn (player), `== 0` means permanent ragdoll (enemies) and optionally drops loot (`LootItemID`/`Quantity`/`DropChance`, rolled with `>=` against `FRand()`).
- **Win condition**: `UALSObjectiveSubsystem : UWorldSubsystem` (not a GameMode — `ALS_GameMode_SP` is a Blueprint, C++ can't subclass it) tracks enemy `AALSEnemyAIController` health components via `OnWorldBeginPlay`, fires `OnAllEnemiesDefeated` once. Tests spawning enemies after world BeginPlay must call `RefreshTrackedEnemies()` again explicitly.
- **Restart**: `UALSRestartLevelComponent` — `P` key, `UGameplayStatics::OpenLevel` on the current level, ungated on win/death state. Not covered by CQTest (tears down the test's own temp world).
- **HUD**: `WBP_StatusBars`/`UALSStatusBarsWidget` — health/stamina/ammo bars, death text, objective/victory text. Verified live only (see the `NativeConstruct` CQTest gap above).

## Known open items / real bugs still outstanding

- Muzzle sockets on M4A1 (verified via debug trace), M9, and Bow (both corrected via `SkeletalMeshTools.get_bounds` cross-check, no debug-trace pass) are geometrically plausible but M9/Bow haven't had a human-eyeball or debug-trace verification pass yet.
- The reload animation's hand/gun offset correction fields exist (`ReloadHeldObjectLocationOffset`/`RotationOffset` on `FALSWeaponAmmoStats`) — see `AGENT_TASKS/0001_rifle_reload_gun_offset.md` for current tuning status.
- **Other UAL animations remain unverified/corrupted** (`AS_Sword_Attack`, `AS_Hit_Chest`, ~9 others). Use the clean GLB pipeline above as the starting point and validate each clip; the old `convert_space` remap and scale-100 import workaround are not the current recipe.
- **Unexpected pelvis scaling: check source reference versus animated root scale first.** The old UAL import had reference scale 100 and animation scale 1; its `scale_vertical=100` compensated for that import error. The corrected source uses both pelvis scales 1. Verify actual poses/settings rather than copying historical calibration.
- **`rename_asset`'s automatic reference fixup repoints existing references to wherever the OLD asset gets renamed TO, not to whatever later takes its place at the original path.** Swapping a wired-in asset (rename old out of the way → rename new into its path) leaves every existing reference pointing at the old asset's new (temp) location — explicitly repoint them back afterward, don't assume the final path takes over automatically.
- **Root-facing corrections depend on the source.** The old Unity-FBX needed a 180° correction; the clean Unreal/Godot GLB does not. Compare against a known-good target pose and account for mesh-to-actor rotation before adding an offset.
- **Verifying a retarget by only comparing frames of the same suspect clip against each other can't catch a systematic (constant) offset** — a 180°-flipped or scale-mismatched bone still looks internally "smooth" and "distinct" across its own timeline. Diff against a known-good animation on the same target skeleton (any working `AS_*` asset) at the same bone, at rest, to establish real ground truth — this is how the `AS_Punch_Cross` root-rotation bug was actually found, after two rounds of scale-only fixes that read as correct in isolation.
- **A crash can silently revert a retargeter/IK Rig asset's *recently-saved* calibration (pelvis scale, rotation offsets) back to an older state**, not just discard unsaved in-memory edits — confirmed by reading the asset back fresh after a crash+relaunch and finding `scale_horizontal`/`root` rotation offset back at values from several fix-iterations earlier, despite `save_asset` having reported success each time. After any crash+relaunch in a session that's been tuning an `IKRetargeter`, always re-read every calibration value (`get_op_controller(N).get_settings()`, `get_rotation_offset_for_retarget_pose_bone(...)`) before trusting it's still correct — don't assume "I saved it earlier" survived. `AssetImportTask`/`import_asset_tasks` calls are the highest-crash-risk step in this whole pipeline (the known `TaskGraph.cpp:705` recursion assertion) — `ping` after each one before issuing the next command, since the crash often doesn't surface until the *following* call.
