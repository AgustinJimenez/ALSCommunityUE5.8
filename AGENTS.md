ALSHost agent notes

This file exists so an agent working on this project does not have to rediscover things a previous session already figured out the hard way. Read it before doing anything nontrivial. Update it when you learn something that would have saved you time if it had already been written down.

What this project is

ALSHost is a minimal UE 5.8 host project built to run and extend the ALS-Community-UE5 locomotion plugin (vendored directly under Plugins/ALS-Community-UE5, not a submodule, since we are not pushing changes back upstream to it). Live editor control comes from two MCP layers: Epic's own ModelContextProtocol plus EditorToolset, and a second, more capable plugin called ClaudeUnrealMCP, which is a git submodule pointing at AgustinJimenez/ClaudeUnrealMCP. The dual setup mirrors what ResidentHorrorV1 already does; see docs/mcp-notes.md for the operational detail. Everything durable we have figured out about this specific codebase lives under docs/: asset-audit.md, mcp-notes.md, architecture.md, testing.md. Read those before re-deriving the same facts.

The core working philosophy: when ClaudeUnrealMCP cannot do something we need, the answer is almost always to add the capability to ClaudeUnrealMCP itself, not to work around the gap forever. That plugin is our own submodule with its own repo; we can and should extend it. The socket-authoring tools (add_socket, set_socket_transform, list_sockets) are the model for this: we hit a wall trying to add a muzzle socket to a weapon skeleton, found the correct engine API by reading Unreal's own SkeletonEditor source, wrote a proper C++ handler, rebuilt, reconnected, and used it live, then committed and pushed to the ClaudeUnrealMCP repo and bumped the submodule pointer here. Do the same thing next time something is missing. A one-off Python or console-command workaround is fine to get unblocked in the moment, but if the same class of problem will plausibly come up again, build the tool.

On Unreal's Python console being more restricted than it looks

A surprising number of UPROPERTYs that are perfectly normal C++ fields are marked in a way that makes them unreadable and unwritable from the Python console, with an error like "Property X for attribute Y is protected and cannot be read." We have hit this for AnimGraph Nodes arrays, for NodeGuid on individual graph nodes, and for Skeleton::Sockets. There is no consistent rule for predicting which properties will be blocked; you find out by trying. When Python refuses, the console command obj dump "<full object path>" almost always still works and prints the real values as plain text, including things like NodeGuid that Python outright refuses to hand back. Full object paths for anything nested inside a Blueprint graph look like a dot-separated walk down through the containment hierarchy, for example AimOffsetBehaviors.AnimGraphNode_StateMachine_0.Aim Offset Behavior States.AnimStateNode_1.Look Towards Camera.AnimGraphNode_StateMachine_0.Look Towards Camera States.AnimStateTransitionNode_75.Transition.K2Node_AnimGetter_0, and any path segment containing a space needs the whole path double-quoted for the console parser. When even obj dump is not enough because you need to mutate the property, not just read it, the fix is a proper C++ MCP handler using the correct native engine API for that property, the same way we solved sockets.

On AnimGraph state machines specifically

A Blueprint's ordinary FunctionGraphs and UbergraphPages, which is what most Blueprint tooling walks by default, do not include the graphs nested inside an AnimGraph state machine. Every state has its own graph, and every transition rule has its own graph, and none of them show up unless you recursively call GetSubGraphs() on every node starting from the top-level graphs, the same pattern used in MCPServerHelpers.cpp's DoesBlueprintReferenceEnum and now also in delete_node. read_function_graphs does not descend into these either, it only sees the top-level AnimGraph. reconstruct_node already did the full recursive walk before we fixed delete_node to match it, which is exactly why reconstruct_node could find a broken node that delete_node could not.

On removing Blueprint graph nodes

Never remove a node via the graph's own raw RemoveNode(). It only drops the node from the Nodes array, it does not break pin links and it does not notify owning Blueprint extensions. For a node inside an AnimGraph state machine sub-graph this leaves AnimBlueprintExtension_StateMachine's cached TargetRootNode dangling, and the editor crashes with an internal engine assertion on the next compile, not immediately, which makes the cause hard to trace back if you are not already suspicious of the removal method. Always use FBlueprintEditorUtils::RemoveNode() instead. This was a real editor crash we hit calling remove_error_nodes, not a theoretical concern, and it is fixed in both delete_node and remove_error_nodes as of ClaudeUnrealMCP commit cbfadf5.

On the MCP connection itself

execute_console_command never returns its command's output in the tool response, including for py scripts; you always have to follow up with read_log or a direct read of the Saved/Logs file to see what actually happened. If a command crashes the editor process outright, the MCP client just sees a generic connection error, indistinguishable at first glance from a network hiccup; check Get-Process -Name UnrealEditor before assuming anything transient. reload_mcp_server hard-restarts the Node bridge process rather than gracefully refreshing it, which kills the calling session's own connection to it, observed as every mcp__unreal-engine-als__ tool becoming unavailable at once; the fix is not a full Claude Code restart, running the /mcp slash command can reconnect a dropped stdio MCP server on its own.

Codex has its own MCP configuration in ~/.codex/config.toml (or a trusted project's .codex/config.toml); it does not read the ~/.claude.json entry documented in the README. Check `codex mcp list` and `codex mcp get <name>` before blaming the editor. We found `unrealMCP` enabled but pointing at a deleted UE5MCPTest checkout while Unreal was healthy and listening on 9877, so no Unreal tools appeared in Codex. Its stdio command must launch this project's `E:/repo/unreal_engine/ALSHost/Plugins/ClaudeUnrealMCP/MCPServer/index.js`, with UE_HOST=127.0.0.1 and UE_PORT=9877. Epic's native server should be registered separately as a Streamable HTTP MCP at http://127.0.0.1:8000/mcp; if port 8000 is not listening, run `ModelContextProtocol.StartServer 8000` in the editor first. A successful TCP listener alone does not prove the whole bridge: validate ClaudeUnrealMCP with an MCP `ping` call (expect `pong`) and the native server with an HTTP initialize request (expect 200). Codex snapshots MCP tools when the client/session starts, so after adding or correcting either entry, restart Codex/ChatGPT Desktop before expecting the tools to appear; changing config cannot inject them into an already-running session.

On the character's held-object and weapon-holding system

AALSCharacter has one HeldObjectRoot scene component with a StaticMeshComponent and a SkeletalMeshComponent both attached under it, meaning a character can hold at most one rigid prop and one animated prop at a time, not an arbitrary number. AttachToHand, a BlueprintCallable C++ function on ALSCharacter.cpp, snaps HeldObjectRoot onto a virtual bone on the character skeleton, either VB RHS_ik_hand_gun or VB LHS_ik_hand_gun, with an optional offset. The actual per-weapon logic lives in Blueprint, in ALS_CharacterBP's OnUpdateHeldObject function, which switches on the character's EALSOverlayState enum and calls AttachToHand with a hardcoded default mesh per case, for example Rifle maps to the M4A1 skeletal mesh. To add a new weapon, either swap the default mesh reference on an existing case's AttachToHand node, or extend the enum and switch for a genuinely new category, or just call AttachToHand directly from custom gameplay code and skip the switch entirely. Weapon meshes in this plugin are SkeletalMeshes with their own tiny per-weapon skeleton, not StaticMeshes, apparently so parts like a bolt or a bowstring can animate; check for sockets on the weapon's own Skeleton asset, not on the character skeleton, when you need a muzzle or grip point. M4A1_Skeleton originally only had one socket, named ADS, meant for aim-down-sights eye alignment; we added a Muzzle socket to it ourselves using add_socket once that tool existed, estimating its position from the mesh's bounding box and planning to nudge it visually once there is a debug laser to check it against.

On fire mechanics, current state as of the last check

UALSWeaponFireComponent lives in ALSHost's own Source module rather than the vendored plugin, added as a component on ALS_CharacterBP, and has been verified working live by the user, not just compiled. It binds its own Enhanced Input actions (IA_Fire on left mouse, IA_Reload on R, both under /Game/ALSHost/Input, IMC_Fire mapping context) directly via BindAction and adds its own mapping context via the EnhancedInput subsystem, rather than routing through ALSPlayerController's name-based action dispatch, specifically so no vendored plugin C++ needed editing. Binding happens both in BeginPlay and via APawn::ReceiveControllerChangedDelegate, because a pawn's BeginPlay commonly runs before its PlayerController actually possesses it and binding only once in BeginPlay silently does nothing when that happens. Fire() traces from the held weapon's Muzzle socket toward a point projected out along the camera's forward vector, not the muzzle bone's own rotation, so the shot visually leaves the barrel but still converges on what the player is actually looking at. Spread is a probability cone sized from EALSGait and tightened when EALSRotationMode is Aiming, escalating further per shot as bloom (recovering after a short pause) rather than being a fixed accuracy number. Firing also kicks the camera pitch per shot via AddPitchInput, the same API normal mouse look uses, so it composes naturally and can be fought by pulling the mouse down, accumulating during sustained fire and settling back over several frames. Full-auto fires once immediately on press then repeats at a RoundsPerMinute-derived interval until release. Ammo is capped per weapon type via a TMap<EALSOverlayState, FALSWeaponAmmoStats> (30 rounds for Rifle by default, the only overlay state configured so far since only the M4A1 has a working Muzzle socket); firing at 0 stops full-auto cleanly instead of clicking on nothing, and Reload() blocks firing for ReloadSeconds before refilling. ALS.Weapon.ShowDebugTrace gates a debug line/hit-marker draw separate from actual hit detection, defaulted to true in code for now since the editor gets restarted often during development and console variables do not persist across restarts - flip back to false once the weapon system is considered done. One real operational gotcha hit along the way: add_input_mapping does not auto-save, and force-killing the editor (Stop-Process -Force, needed for every C++ rebuild) discards unsaved changes - always save_asset immediately after add_input_mapping, we lost a key mapping this way once already.

On automated testing, or the current lack of it

We tried to verify the fire component by calling Fire() directly on the live PIE player pawn instead of needing a human to click, and hit a real wall: every actor-query tool available, list_actors, find_actors_by_name, get_scene_summary, and raw Python GameplayStatics.get_all_actors_of_class(None, ...), all resolve to the editor world, not the running PIE world, even while PIE is genuinely playing. Level-placed actors are visible in both because they get duplicated in at PIE start, but anything spawned dynamically at runtime, including the player pawn itself, only exists in the PIE copy and is invisible to every tool tried. There is currently no known way to reach a live PIE actor through this MCP setup at all. The actual, correct way UE5 projects solve this is not through MCP in the first place: Epic's Automation System runs tests as code compiled into the engine process itself, discovered and run from the Session Frontend Automation window or headlessly via -ExecCmds="Automation RunTests Name;Quit", so a test's own GWorld correctly follows into PIE because the test is engine code, not an external client reaching in afterward. The specifically relevant piece for us is CQTestEnhancedInput, a plugin shipped with the engine that programmatically injects Enhanced Input actions into a pawn via the real input-injection API and can spawn a test map to find the player pawn, which is exactly our scenario. See docs/testing.md for the concrete, scoped plan; not implemented yet, but the investigation is done so it does not need repeating.

On pulling animations in from another project and retargeting them

ALS-Community-UE5's own content has no reload animation anywhere (checked directly, not assumed - searched for "Reload" across the whole plugin and found nothing). ResidentHorrorV1, a separate store-bought template project in this same parent directory, does have real reload montages and their underlying AnimSequences (AS_MM_Rifle_Reload etc.), targeting the stock Epic SK_Mannequin skeleton rather than ALS's own ALS_Mannequin_Skeleton, so they are not directly usable as-is - an AnimSequence is bound to one specific Skeleton asset, and duplicating the file does not change that. The bone hierarchy turned out to be effectively identical though: walking ALS_Mannequin_Skeleton's actual bones live (via SkeletalMeshEditorSubsystem.get_bone_children starting from 'root') showed the exact standard Epic UE5 Manny naming - root, pelvis, spine_01 through 03, clavicle/upperarm/lowerarm/hand_l/r with full finger chains, thigh/calf/foot/ball_l/r, ik_foot_root, ik_hand_root - which is exactly what SK_Mannequin also uses, ALS just adds its own extra virtual bones (VB LHS_ik_hand_gun etc, the ones AttachToHand already relies on) on top rather than renaming anything. That match is what made retargeting actually work cleanly rather than needing a full IK Rig setup.

The pipeline that worked, done twice now and both pieces genuinely scriptable with no editor UI clicking required at any point once the tooling existed: first, IAssetTools::MigratePackages(PackageNames, DestinationPath, FMigrationOptions) - discovered to be UFUNCTION(BlueprintCallable) and thus Python-exposed as AssetToolsHelpers.get_asset_tools().migrate_packages(...), with FMigrationOptions.bPrompt's own doc comment saying "always false through scripting" confirming Epic built this specifically for automation. This has to run from the SOURCE project's own editor session, not the destination's, since it operates on that project's currently-loaded asset registry and our MCP bridge is just a TCP client that talks to whichever editor happens to be running on port 9877 - meaning closing ALSHost's editor and opening ResidentHorrorV1's instead (both being UE 5.8) was the only way to reach ResidentHorrorV1's assets at all, then closing that and reopening ALSHost afterward to keep working. Second, once the animation and its dependencies had landed in ALSHost's own Content folder, actually reassigning it onto ALS_Mannequin_Skeleton needed a real new ClaudeUnrealMCP tool: EditorAnimUtils::RetargetAnimations(), the function the classic "Retarget Skeleton" Content Browser right-click action calls internally, is plain C++ free functions in the UnrealEd module with zero Blueprint or Python exposure - directly setting an AnimSequence's Skeleton property via Python fails outright with "read-only and cannot be set". retarget_anim_asset now wraps it (ClaudeUnrealMCP commit 591d44f); it produces a new duplicate on the target skeleton without touching the source, and worked correctly on the first real attempt, verified via SequenceLength/frame count matching the source and a clean AssetRegistry dependency check before deleting the migrated staging import (442MB across 139 files, almost all of it ResidentHorrorV1's own Control Rig pose library dragged in as a dependency of the one animation we actually wanted - safe to delete once retargeting produces a fully independent asset, checked via get_dependencies returning nothing under the source project's path).

One real snag along the way: EditorAssetLibrary.delete_directory on the 139-file staging import triggered what was almost certainly a blocking confirmation dialog - the MCP connection timed out entirely (ping and everything else) while Get-Process still reported the editor as "Responding" (Windows only flags a process as truly hung when it stops pumping window messages, which a modal dialog waiting for a click does not do). Nothing could be done about it from the MCP side; needed the user to physically find and click through the dialog in the editor window before the connection came back. Worth remembering before triggering any bulk-delete style operation headlessly - it may need a human on standby, not just wait longer.

On architecture and what is and is not converted to C++

ALS-Community-UE5 has roughly 8100 lines of real C++ covering the character, movement component, camera, mantling, debug, math library, AI controller and behavior tree tasks, and the animation data layer via ALSCharacterAnimInstance. ALS_AnimBP, the actual AnimGraph, is Blueprint and always will be, because Unreal's AnimGraph is structurally an editor construct with no supported pure-C++ authoring path, in any project, however C++-heavy. This is not a sign of incomplete conversion. Every other Blueprint class in the plugin, checked directly via read_blueprint rather than assumed from its name, turned out to be either a thin config subclass of an already-C++ parent, an editor-time AnimModifier asset-baking script, or genuinely trivial content like a camera shake curve or a demo-level decoration actor. See docs/architecture.md for the full breakdown.

On a batch of new ClaudeUnrealMCP crash bugs found while building a live reload-offset tuning tool

Trying to build an in-PIE debug tool (hold T to equip the rifle, loop the reload animation, and tweak HeldObjectRoot's location/rotation offset via UMG sliders while watching it live) surfaced three real ClaudeUnrealMCP bugs, all fixed, none committed/pushed yet as of this writing. First: add_widget constructed new widgets via WidgetTree->ConstructWidget directly, bypassing FWidgetBlueprintEditorUtils::CreateWidget, which is what actually registers a GUID for the new widget in UWidgetBlueprint::WidgetVariableNameToGuidMap. Most widget types tolerated the missing entry, but adding a Button hit the compiler's own internal consistency check (WidgetBlueprintCompiler.cpp, ensure "Widget was added but did not get a GUID") as a hard crash, not just an ensure - fixed by explicitly adding a fresh FGuid to that map for every widget add_widget creates, harmless even for widgets that never become Blueprint variables. Second, and worse: set_component_property's generic FObjectProperty branch is reached by FClassProperty too, since FClassProperty derives from FObjectProperty, so setting a TSubclassOf<T> property (we hit this on DebugReloadTuningWidgetClass) loaded the target as a plain UObject and stored a UWidgetBlueprint *asset* directly into a UClass* slot - the property set call itself reports success, no error, but the corrupted property later crashes the editor on save/serialize with an unrelated-looking assertion deep in PropertyClass.cpp. Fixed by checking CastField<FClassProperty> first and resolving through the Blueprint's GeneratedClass when the loaded object is a UBlueprint rather than already a UClass. Third, a genuine gap rather than a crash: set_widget_property only ever looked up the property on the widget's own class, so nothing that lives on a child's UPanelSlot (Size, Padding, HorizontalAlignment - the FSlateChildSize Size property is what actually makes a Slider fill real width inside a HorizontalBox row instead of using its tiny auto-sized default) was reachable at all; fixed by falling back to Widget->Slot's class when the property isn't found on the widget class first.

On set_component_property not forcing a Blueprint recompile

A genuinely confusing one: set_component_property only calls FBlueprintEditorUtils::MarkBlueprintAsModified, which flags the Blueprint dirty but does not itself trigger FKismetEditorUtilities::CompileBlueprint. read_component_properties reads straight off the SCS ComponentTemplate, so it always shows your just-set value correctly, and save_asset succeeds - both give every appearance the change took. But PIE spawns actors from the Blueprint's already-compiled generated class, which is a separate baked copy produced at compile time; if nothing forces a recompile in between, PIE keeps running the old generated class indefinitely, silently ignoring the new value with zero errors anywhere. We burned a long diagnostic loop on exactly this: DebugReloadTuningWidgetClass read back correctly from the Details panel every time, yet CreateWidget in PIE never even attempted construction (confirmed by temporary UE_LOG statements never firing) until an explicit compile_blueprint call was made against the Blueprint. Rule going forward: after any set_component_property (or similar raw-property-mutation tool) whose effect needs to show up in PIE, follow it with an explicit compile_blueprint call before testing, not just save_asset.

On the reload animation hand/gun offset problem, current status

AS_Rifle_Reload (see the retargeting paragraph above) plays correctly as an animation in isolation - opening it directly in Persona shows a normal-looking reload motion. The problem is specifically that the M4A1's grip position/rotation looks wrong relative to the hands while it plays, because the rigid weapon attach (HeldObjectRoot snapped once to the VB RHS_ik_hand_gun virtual bone with a static Offset - see the held-object paragraph above) has no way to know this animation was authored against a different weapon's grip geometry in the source project. UALSWeaponFireComponent already has ReloadHeldObjectLocationOffset/RotationOffset fields on the per-weapon FALSWeaponAmmoStats struct specifically to correct this, applied additively to HeldObjectRoot for the duration of Reload() (and reverted after) - editable directly in ALS_CharacterBP's WeaponFireComponent Details panel under Ammo Stats By Overlay State -> Rifle, no debug tool required, and this path uses the normal R-key Reload() flow which has been solid the whole time. The still-unresolved piece is figuring out the actual correction numbers; a new compare_anim_bone_pose ClaudeUnrealMCP tool was added for this (wraps UAnimPoseExtensions::GetAnimPoseAtTime/GetBonePose, not otherwise exposed to Blueprint or Python) to diff a bone's world/component-space transform between two animations at given times - e.g. AS_Rifle_Reload against ALS-Community-UE5's own /AdvancedLocomotionV4/CharacterAssets/MannequinSkeleton/AnimationExamples/Overlay/M4A1/ALS_Props_M4A1_Aim_Sweep, a known-good reference animation for holding this exact rifle. If hand_r's delta between the two is roughly constant across sampled times, that delta is directly usable as the two offset fields; if it drifts a lot frame to frame, a constant offset cannot fix it and the honest answer is a manual animation-editor touch-up, not more automation. See AGENT_TASKS/0001_rifle_reload_gun_offset.md for the live, blow-by-blow state of this specific task.

On the debug reload-offset tuning tool's architecture, and why it is not built as a normal Blueprint UI

WBP_RifleReloadTuning is reparented to a small new C++ class, UALSRifleReloadTuningWidget (Source/ALSHost/Public+Private/UI), rather than having its slider/button logic wired as Blueprint event-graph nodes the way a human would build it in the Designer. The reason is a real capability gap, not a style preference: ClaudeUnrealMCP has add_set_struct_node for one specific purpose and connect_nodes/set_pin_default for wiring already-existing nodes, but no generic "add a K2Node_CallFunction / K2Node_Event / bind-a-widget-delegate" tool, so there is no way to author an OnValueChanged or OnClicked handler graph through MCP at all right now. The widget's Slider_*/Value_*/CopyButton/FreezeButton members use meta=(BindWidget) (BindWidgetOptional for ones added after the initial reparent, so an in-between rebuild before the matching content-side add_widget call does not hard-fail Blueprint compilation), so the WBP only needs matching widget names in its tree - everything else, including reading/writing UALSWeaponFireComponent's DebugGetReloadLocationOffset/DebugSetReloadLocationOffset/etc, lives in native NativeConstruct()/OnXChanged() code. If a future task needs real Blueprint-graph authoring through MCP (not just this widget), that is the gap to build a tool for next, the same way sockets and retargeting got built when they were the blocker.

On the older engine stack this plugin uses versus newer alternatives

ALS-Community-UE5 is built on CharacterMovementComponent and blend-space-driven locomotion, which its own maintainers have called outdated and put the repo into maintenance-only mode over. GASP-ALS-R, a separate project also set up in this same parent directory, uses Epic's newer stack instead: Mover for movement, Motion Matching and Pose Search for animation, and the Gameplay Ability System for abilities. ClaudeUnrealMCP currently has thin scaffolding for GAS, being able to create GameplayAbility and GameplayEffect Blueprints and not much more, and has zero support at all for Mover or for Motion Matching and Pose Search, checked directly in the source, not assumed. If this project or a successor moves onto that stack, expect to repeat the same shape of work documented above: hit a gap, trace the exact engine API, extend ClaudeUnrealMCP, ship it. See docs/mcp-notes.md for the fuller writeup of this specific gap.

On building a replacement debug prop-picker menu, and the two bugs that made it not work at first

ALS-Community's own Q-held debug overlay menu (DebugComponent's OpenOverlayMenu/OverlayMenuCycle, driving an OverlayStateSwitcher widget) is genuinely broken vendored content, not something we broke: its OverlayStateButtons array is never populated anywhere in its EventGraph (traced fully, not assumed), so scrolling never worked and there was nothing to click either. Rather than keep patching a Blueprint with no working foundation, we built a full native-C++ replacement: UALSOverlayStateOptionWidget (one clickable/hoverable row, NativeOnMouseButtonDown/Enter/Leave overrides calling SetOverlayState directly) and UALSDebugPropMenuWidget (container that enumerates every EALSOverlayState value via StaticEnum<EALSOverlayState>() and spawns one row per value), wired into UALSWeaponFireComponent's existing Q-bound DebugOverlayMenuInputAction/InputMappingContext. Two real bugs surfaced getting this working, both worth knowing about before building UMG content through MCP again:

First, rows had no working hover or click at all despite the C++ being correct and compiled. Cause: create_widget_blueprint's default root is a CanvasPanel, and a CanvasPanel-rooted UUserWidget instance reports no meaningful desired size when embedded as a child of an auto-sizing container (AddChildToVerticalBox) - it rendered at effectively zero size, so no hit-testing ever reached it. There was also no existing tool to restructure an already-built widget tree, only add_widget (new widgets only) - built remove_widget (wraps UWidgetTree::RemoveWidget, rejects removing the root) to fix this class of problem going forward. The actual fix was nesting a SizeBox (explicit WidthOverride/HeightOverride) between the root CanvasPanel and the Border/TextBlock content, which gives the row a real, container-respected size. Lesson: any UUserWidget meant to be embedded in a Vertical/HorizontalBox (not placed directly in a viewport) needs a SizeBox, ScrollBox, or similar content-driven-size panel somewhere in its tree, never a bare CanvasPanel root.

Second, and much sneakier: after fixing clicking, selecting an overlay state worked visually but silently reverted to Default the instant Q was released. Spent a real cycle chasing this as an Enhanced Input mapping-context ordering problem (suspending PC->DebugInputMappingContext alongside DefaultInputMappingContext while our menu is open) before proving that theory wrong - the revert kept happening identically after that fix shipped and rebuilt. The actual cause, found by reading DebugComponent's EventGraph in full (read_event_graph_detailed, then walking node connections/pins in a small Node.js script since the JSON is too large to eyeball - see the tool-results file it saves to on truncation): DebugComponent's OpenOverlayMenu(bValue) event's "menu closed" (bValue=false) branch unconditionally calls SelectOverlayState on its own OverlayStateSwitcher widget before removing it, which forces the character's overlay state back to whatever that (broken, never-updated-by-us) widget's internal selection is - always Default, since nothing had ever set it. This ran independent of whichever mapping contexts were active, which is why suspending contexts didn't touch it - it's a straight Blueprint call chained off the same shared Q input action, not something input-context priority can gate once the event has already fired. The real fix was going into that vendored Blueprint directly and removing the harmful call: disconnect_pin on the predecessor node's exec pin, connect_nodes straight to the next node in the chain (skipping SelectOverlayState entirely), then delete_node on SelectOverlayState itself, compile_blueprint, save_asset. No C++ rebuild needed since it's a content-only Blueprint edit. Lesson: when a symptom looks like an input-routing/timing problem but a fix at that layer doesn't change anything, check whether a *Blueprint event on the same shared trigger* is doing something unconditional downstream - input-context suspension only prevents an event from firing, it does nothing to stop logic already wired to fire off a Blueprint event we don't otherwise control, and the fix has to be surgery on that Blueprint's graph, not more C++.

Also worth remembering: plugin content isn't mounted at a path matching its folder name or FriendlyName - it's mounted under the plugin descriptor's actual .uplugin filename (ALS-Community-UE5's is ALSV4_CPP.uplugin, so its content root is /ALSV4_CPP/..., not /ALS-Community-UE5/... or /AdvancedLocomotionV4/...). search_assets and list_blueprints only ever searched /Game and came up empty for plugin content no matter what path_filter was passed; the reliable way to find a plugin asset's real in-editor path is grepping the raw .uasset file on disk for /Script/Engine.BlueprintGeneratedClass strings (e.g. `strings -n 8 DebugComponent.uasset | grep DebugComponent`), which prints the exact package path Unreal itself uses.

On nested/sub menus in this menu system, and a repeat of the unsaved-property-lost-on-force-kill bug

Extending the replacement menu to support a submenu (a "Debug Modes >" row that opens a second panel to the right, listing the existing DebugStartReloadOffsetTuning/ToggleDebugReloadAnimLoop/ToggleDebugReloadFreeze/DebugCopyReloadOffsetsToClipboard debug actions that previously only had a tap/hold "T" gesture) needed a shared row base class - UALSDebugMenuRowWidget now holds the hover/click/label chrome (a TFunction<void()> click handler set via SetOnClicked, no Blueprint delegate involved), and both UALSOverlayStateOptionWidget and the new generic rows derive from or are constructed as it directly. The submenu (UALSDebugModesMenuWidget) is not a Designer-nested child of WBP_DebugPropMenu's static tree - ClaudeUnrealMCP has no tool to embed one Widget Blueprint's instance inside another's tree at design time, so it's created dynamically in NativeConstruct via CreateWidget and added to the parent's own root CanvasPanel via UCanvasPanel::AddChildToCanvas, with its UCanvasPanelSlot positioned via SetAnchors/SetAlignment/SetOffsets in C++ (point-anchor semantics: when Anchors.Minimum==Maximum, FMargin's Left/Top become an X/Y position offset from the anchor point and Right/Bottom become width/height, with Alignment choosing the pivot corner). Toggled via SetVisibility(Collapsed/Visible) rather than Add/RemoveFromViewport, since it's a permanent child of the already-viewport-attached parent.

Two real snags:

First, the submenu's outer CanvasPanelSlot was sized narrower (250 wide) than the SizeBox-wrapped rows inside it (280 wide) - a CanvasPanel child with an explicit point-anchored size clips its content to that box for both rendering AND hit-testing, so this produced exactly two symptoms at once from one cause: text visibly overflowing the panel's edge, and clicks on the rows not registering at all. Fixed by widening the outer slot past the rows' width, and separately switched the rows to AutoWrapText plus a smaller explicit Font (the stock UMG TextBlock default size, 24pt, is far too large for a debug-menu row and was part of why long labels like "Copy Reload Offsets To Clipboard" didn't fit). Lesson: when a nested/embedded UMG widget's content overflows its container, treat the interactive symptoms (missing clicks) as suspect too, not just the visual ones - a size mismatch between an outer clipping container and inner content can silently eat hit-testing on the clipped portion.

Second, and this is a repeat of a lesson already written down once this session but worth restating because it bit us again: after using set_blueprint_cdo_property to point WBP_DebugPropMenu's GenericRowWidgetClass/DebugModesMenuWidgetClass at the new content, compile_blueprint and read_class_defaults both confirmed the values were set - but save_asset was never called on that specific Blueprint before several subsequent taskkill/rebuild/relaunch cycles (needed for unrelated C++ changes), which silently discarded both properties back to None. Symptom looked exactly like a code bug ("the Debug Modes row doesn't appear at all") but was purely an unsaved-content-change problem, caught by re-running read_class_defaults after the fact and seeing None where a class reference should have been. The rule from earlier in this file ("always save_asset immediately after set_component_property/reparent_blueprint") applies equally to set_blueprint_cdo_property and really to any content mutation whatsoever - there is no tool in this set that auto-saves, and force-killing the editor (required before every C++ rebuild) is completely indiscriminate about what unsaved changes it throws away. Going forward: treat every single content-mutating MCP call as needing its own save_asset before doing anything that could trigger a force-kill, and when a feature "isn't working" after any rebuild+relaunch cycle, re-verify every property that was set before the rebuild via read_class_defaults/read_component_properties/inspect_asset before assuming the bug is in the code - this class of bug is common enough now that it should be the first thing checked, not the last.

On real automated gameplay tests (CQTest), and closing the PIE-blindness gap for good

On level-placed actors silently reverting after a force-kill, even when save_asset succeeded and was verified

A third variant of the "force-kill discards more than you'd expect" family, distinct from the CDO-property one above: placed a test enemy and two pickups in ALS_DemoLevel, called save_asset, and even re-verified via get_current_level's actor_count (139, correct) and the .uasset file's disk mtime (updated) before moving on - by every check available, this was genuinely saved. It still reverted to 136 actors (all three additions gone) after a later force-kill+relaunch cycle for an unrelated C++ rebuild, and the disk file's mtime and git status both still showed the correct 139-actor version untouched. The cause: `Saved/Autosaves/.../ALS_DemoLevel_Auto1.umap`, a periodic editor autosave snapshot, existed with a timestamp only ~2 seconds older than the real save - the editor appears to prefer restoring from a recent autosave over the actual saved package on a next launch after an improper shutdown (which a force-kill always is), silently, with no dialog blocking the MCP connection this time (unlike the modal-dialog case documented elsewhere in this file). Deleted the stale autosave once found. This is now the third distinct thing (after unsaved Blueprint CDO properties, and this) that can make "I saved and verified it" turn out not to have stuck by the next session - the operating rule going forward is to re-run get_current_level/find_actors_by_name (not just trust a prior save) after any relaunch, any time placed-actor state actually matters, and to check Saved/Autosaves for a suspiciously-recent file if actors vanish despite the disk .uasset looking correct.

**Correction/follow-up**: the autosave theory above was probably a misdiagnosis, or at best only ever half the story. The exact same symptom recurred in a later session with zero autosave files present at all. This time the check was pushed one level deeper: `git status` on the .uasset showed clean (matched HEAD) and the file's mtime looked plausible, but grepping the raw bytes on disk (`strings -a ALS_DemoLevel.uasset | grep BP_EnemyBasic_C_0`, the actual spawned actor's object name) found nothing - the actors were never actually in the committed file's bytes in the first place, despite `save_asset` having returned `"saved": true` and `get_current_level`'s actor_count having read back correctly *in the same live editor session* right after. The likely real mechanism: `save_asset`'s success response and `get_current_level`'s actor count both read in-memory/already-known state, neither one proves the physical package write to disk actually completed and flushed before the next command runs (UE5's SavePackage can involve async I/O). The fix that actually worked: after `save_asset`, wait a few seconds, then grep the raw .uasset bytes on disk for the specific actor's exact object name (not just check mtime or git status, both of which can also reflect a stale-but-self-consistent prior state) before trusting the save enough to `git commit` it. Do this any time level-placed actor state needs to survive to a future session - it is cheap and it is the only check in this whole family of gotchas that has actually caught the problem *before* committing, rather than after the fact.

**Second correction - the actual root cause, found for real this time**: both corrections above were still wrong, or at best treating a symptom. A session asked to place more pickups found the level back down to its pre-any-placement vanilla actor count *yet again*, despite every check in the paragraph above having been followed correctly the previous session (byte-grep on `ALS_DemoLevel.uasset` after `save_asset` + a wait had found the actors present, and that was verified again in the committed git blob before pushing). The break this time: `ALS_DemoLevel` is a **level/world package**, whose correct file extension is `.umap`, not `.uasset` - but the file every previous session had been writing to, byte-grepping, and committing was a stray `ALS_DemoLevel.uasset` sitting right next to the real `ALS_DemoLevel.umap`. `git log` on that `.uasset` path showed it first appearing in the commit that did the *first ever* `save_asset` call against this level, not in the initial commit - it was never a real, pre-existing asset. The actual `ALS_DemoLevel.umap` had an untouched mtime from the initial commit and, checked directly, held none of the placed actors. Root cause, found by reading ClaudeUnrealMCP's own source rather than guessing again: `FMCPServer::HandleSaveAsset` (and `HandleSaveAll`) in `MCPServerBlueprintLifecycle.cpp` built the save filename with `FPackageName::LongPackageNameToFilename(Package->GetName(), FPackageName::GetAssetPackageExtension())` unconditionally - always `.uasset`, even when the package's top-level object is a `UWorld`. Every `save_asset` call against a level for the entire history of this project's "level actor state reverts" saga was silently writing to a bogus, wrongly-extensioned file the editor never loads on startup, while the real `.umap` sat untouched. Fixed in both handlers by checking `Package->ContainsMap()` and using `FPackageName::GetMapPackageExtension()` (`.umap`) when true - a real engine API pair built for exactly this. Verified by placing actors, saving, byte-grepping the *correct* `.umap` file (confirmed present), then a full `taskkill`+relaunch cycle (confirmed still present via `get_current_level`'s actor count) - the first time this whole family of bugs has actually been proven fixed by surviving a real restart, not just inferred from a disk check. The stray `.uasset` was deleted and `git rm`'d. Lesson under the "when ClaudeUnrealMCP cannot do something we need, extend it" philosophy at the top of this file: a tool that reports success and even produces a real, correctly-formatted file on disk can still be silently writing to the *wrong* file entirely - when a symptom this specific and this repeatable survives two rounds of "fixes" that both seemed to work in the moment, check the tool's own source before trying a third patch on the calling side.

On actually getting Epic's own ModelContextProtocol server connected (it was documented as part of the setup, but was never actually live in a session before)

The opening paragraph of this file already described the intended dual-MCP setup (Epic's ModelContextProtocol + EditorToolset, plus ClaudeUnrealMCP), and `ModelContextProtocol` shows `"Enabled": true` in `ALSHost.uproject` - but no prior session had ever actually gotten Epic's server connected and callable in Claude Code itself, only ClaudeUnrealMCP. Two real things had to happen, neither of which was in the .uproject already being "enabled":

First, the server doesn't auto-start: run `ModelContextProtocol.StartServer 8000` as a console command in the live editor (via `execute_console_command` over ClaudeUnrealMCP, or typed directly) - confirmed via `LogModelContextProtocol: Starting MCP server on port 8000` and a listening TCP port. It does not persist across editor restarts any more than any other console-only state does in this project (same caveat as `ALS.Weapon.ShowDebugTrace`) - expect to re-run it after every relaunch until something starts it automatically.

Second, and the one that actually cost the time: Claude Code's own MCP server registration (`claude mcp add --transport http unreal-engine-official http://127.0.0.1:8000/mcp`) is keyed in `~/.claude.json` by an exact project directory string, and **that key is not necessarily the directory this session's Bash tool has as its cwd**. Running `claude mcp add` from a Bash call with cwd `E:/repo/unreal_engine/ALSHost` registered the server under that key - but the actual live interactive session's own project scope turned out to be the *parent* directory, `E:/repo/unreal_engine` (matching the "Primary working directory" stated in the system prompt, not the subfolder this project's files live in). The already-working `unreal-engine-als` (ClaudeUnrealMCP) entry was registered under that parent-directory key too, which is the tell: `grep -n '"unreal-engine-als"' ~/.claude.json` and look at which `"E:/repo/..."` block it falls under - that's the real scope to add any new project-scoped server under, not wherever a Bash `pwd` happens to say. `/mcp` (reconnect) only re-establishes servers the session already knows about; it does not discover a server added to a *different* scope, or even added to the *right* scope after the session already started - a full CLI restart was needed before the newly-added server actually showed up in `ToolSearch`/tool calls, confirmed independently connectable the whole time via `claude mcp list` (a fresh, stateless subprocess) which is a good way to sanity-check "is the config right" separately from "does this session see it yet."

Once actually connected, discovery is three meta-tools, not a flat tool list (unlike ClaudeUnrealMCP): `list_toolsets` -> `describe_toolset(name)` -> `call_tool(toolset_name, tool_name, arguments)`. Toolsets worth reaching for that ClaudeUnrealMCP has no equivalent of at all: `MaterialTools`/`MaterialInstanceTools`, `TextureTools`, `StaticMeshTools`, `DataTableTools`/`CurveTableTools`/`StringTableTools`. Two more are genuinely better than what we have: `SceneTools.trace_world(start, end)` is a real line-trace query (nothing in ClaudeUnrealMCP does this - we've only ever eyeballed socket/offset positions from bounding boxes and mesh names, e.g. the Muzzle sockets on M9_Skeleton and Bow_Skeleton added this session, still unverified against the actual mesh geometry); and `SceneTools.find_actors` supports type/tag/bounds/collision-channel filtering, richer than `find_actors_by_name`'s name-pattern-only matching.

One thing to not conflate: `SkeletalMeshTools.add_socket` (official) takes a **SkeletalMesh** asset and attaches a mesh-level socket, whereas ClaudeUnrealMCP's `add_socket` takes a **Skeleton** asset (skeleton-level, shared across every mesh bound to it). These are different layers in Unreal's own socket resolution (a mesh-level socket of the same name overrides a skeleton-level one) - all of this project's existing Muzzle/ADS sockets were added at the skeleton level via ClaudeUnrealMCP. Don't add a same-named socket via the other tool without knowing which layer already has it, or the two will silently disagree about where "Muzzle" actually is.

Unfinished, worth picking up: use `SceneTools.trace_world` (or a comparable transform query) to actually verify/correct the M9 and Bow Muzzle socket positions instead of leaving them as bounding-box guesses - the same kind of refinement the M4A1's Muzzle socket got only once a debug laser/trace existed to check it against, per the held-object paragraph above.

On a `MigratePackages` Python argument-type trap that silently "succeeds" while writing a garbage file

`AssetTools.migrate_packages(package_names_to_migrate, destination_path, options)`'s first parameter is `TArray<FName>` (package path strings), not `TArray<UPackage*>`. Passing `unreal.Array(unreal.Package)` filled with `unreal.load_package(...)` results does **not** raise a Python TypeError the way passing a plain Python `list` does (that fails loudly with "Cannot nativize 'list' as 'PackageNamesToMigrate'") - it silently nativizes each `UPackage` object via its string repr instead, and `MigratePackages` happily "succeeds," logging a message like `Package (/Script/CoreUObject.Package'/Game/Foo/Bar') was migrated successfully as (/Game/CoreUObject.Package'/Game/Foo/Bar')` and writing to a garbage destination filename that literally contains `CoreUObject.Package'/Game/...'` as part of the path. Nothing about the tool call result indicates failure - the only tell is reading the actual `AssetTools:` log line (via `read_log`/grepping the log file, since `execute_console_command` never returns output directly) and noticing the package name isn't a clean `/Game/...` path. The fix: build the array as `unreal.Array(unreal.Name)` and `.append(unreal.Name('/Game/Foo/Bar'))` - plain package path strings, not loaded objects. Hit this migrating `SM_knife1` from ResidentHorrorV1; the garbage output folder (`Content/CoreUObject.Package'/...`) had to be deleted by hand before retrying correctly.

On a CQTest crash from capturing a `TEST_METHOD` local by reference in a deferred `.Then()` lambda

`TestCommandBuilder`'s `.Then()`/`.WaitDelay()` chain doesn't run synchronously inside the `TEST_METHOD` call - it registers deferred commands that execute on later engine ticks, after `TEST_METHOD` has already returned. Every working test file in this project (`ALSPickupTests`, `ALSDamageZoneTests`, `ALSWeaponFireInputTests`, etc.) stores actor/component pointers as `TEST_CLASS` member fields for exactly this reason. A first draft of `ALSInteractionTests.cpp` instead declared pointers (`AALSDoor* Door = nullptr;`, etc.) as ordinary locals inside `TEST_METHOD` and captured them into the `.Then()` lambdas by reference (`[this, &Door]`) - this compiles fine and even runs the *first* `.Then()` block correctly (which still executes while the stack frame is technically alive, or at least before UB manifests), but the *second* `.Then()` block, running after a `WaitDelay`, dereferenced a reference to a long-dead stack slot and crashed with `EXCEPTION_ACCESS_VIOLATION` reading a near-null address, with the crashing frame pointing straight at the lambda's line in the callstack. Fixed by moving every pointer that needs to survive across a `.Then()`/`WaitDelay()` boundary into a `TEST_CLASS` member field instead of a `TEST_METHOD` local. Rule going forward: never capture a `TEST_METHOD`-local pointer by reference into a `TestCommandBuilder` lambda that isn't guaranteed to run before the method returns (i.e. never across a `WaitDelay` or `StartWhen`) - promote it to a member field first.

On weapon pickups needing a real weapon mesh, and two MCP tool quirks found doing it

`AALSWeaponPickup` (level-dropped weapon pickups) inherited `AALSPickupBase`'s placeholder `UStaticMeshComponent` (a Cube/Sphere) and never overrode it, so every dropped weapon in the level showed as a generic shape. Verified this by setting via both paths and finding only the function-based read agreed with what actually rendered/persisted through a restart. (2) `capture_screenshot` reported success and a destination path every time it was called (tried 3x, different filenames) but never actually produced a file anywhere on disk in this environment (checked `Saved/Screenshots/` and the whole `Saved/` tree) - treated as a tool limitation for now rather than investigated further; the functional getter-based verification above is the reliable fallback when a visual screenshot check would otherwise be wanted.
